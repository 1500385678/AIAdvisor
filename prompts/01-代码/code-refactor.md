# 代码重构(可读性 + 性能 + 可维护性)

> 场景:对一段工作正常但"难读 / 慢 / 难维护"的代码做系统性重构,产出可落地改动 + 回归验证清单
> 适用模型:Claude (Sonnet/Haiku)、GPT-4o 均可 · 国内模型(DeepSeek/通义)也可用
> 难度:⭐⭐
> 作者/日期:31-智能 cron · 2026-08-27

## 提示词

```
你是一位资深<语言>工程师,擅长在"行为不变"前提下做代码重构。请基于以下信息,按"诊断 → 分级 → 方案 → 验证"四步输出。

【输入】
- 代码文件:<路径:行号范围> + 完整片段(若 ≤ 100 行则全贴,否则贴关键函数)
- 重构目标:<可读性 / 性能 / 可维护性 / 全部 · 排序后输出>
- 约束:<保留 API 兼容 / 不引入新依赖 / 不改测试 / 团队代码风格>
- 风险容忍:<敢动架构 / 只动局部>

【分析要求】
1. **诊断**:先列出 ≥ 3 个"代码异味"(code smell),每条引用具体行号或函数名
2. **分级**:把异味按"高/中/低"优先级排,高=影响维护或性能,中=可读性问题,低=风格问题
3. **方案**:对每个"高"级异味,给出重构方案(含具体改法 + 改后伪代码)
4. **验证**:输出回归测试清单(必须跑哪些 case 才能确认行为不变)

【输出格式】
```
【代码异味清单】
1. [高] <异味名> — <行号/函数> — <为什么是问题>
2. [中] ...
3. [低] ...

【重构方案(仅高优先级)】
异味 1:<名>
  改法:<1 句话技术方案>
  伪代码:
    <before>
    <after>

异味 2:<名>
  ...

【回归测试清单】
- [ ] <case 1:输入 X,期望输出 Y>
- [ ] <case 2:边界条件>
- [ ] <case 3:异常路径>
- [ ] <原测试集全部通过>

【风险点】
- <改后可能影响什么,如性能反而下降 / API 行为微妙变化>
```

【约束】
- 不改业务行为(behavior-preserving),只在结构/可读性/性能上动刀
- 不引入新依赖(除非明确要求)
- 改后行数不应暴增(允许 ±20% 浮动)
- 整体输出 ≤ 500 字
```

## 适用边界

- **适用**:
  - 已有功能正常、需要"清理"或"提速"的代码
  - 单文件 / 单模块 / ≤ 300 行的局部重构
  - 已知 code smell(长函数 / 重复代码 / 复杂条件 / 魔法数字)
- **不适用**:
  - 业务行为需要变更(那是 feature 改写,不是重构)
  - 跨服务 / 跨模块的架构调整(超出 prompt 单文件上下文)
  - 性能瓶颈需 profiling 数据才能定位的场景(模型看不到 hot path)
- **已知坑**:
  - 模型倾向"过度抽象"(动辄引入 Strategy / Factory),需明确"不要新增抽象层"
  - 性能优化的"过早优化"陷阱,模型会瞎改循环结构,需提示"先 profile 再改"
  - 团队代码风格(命名 / 缩进)模型不知道,需贴 .editorconfig 或示例

## 变体 A · 仅可读性(纯清理,不动性能)

在【重构目标】里只写"可读性",并加:
```
【红线】不改任何运行时行为,不改性能特征,不改 API 签名,只动命名/抽取/顺序。
```

适用:code review 阶段、PR 合并前清理

## 变体 B · 性能专项(需 profile 数据)

把【输入】改为:
```
- 性能瓶颈定位:<profile 结果 + hot path 占比>
- 目标:<延迟降 50% / 内存降 30% / 吞吐量提升 2x>
- 已知优化手段:<已尝试过的,如缓存/批处理/算法替换>
```

适用:已 profile 过、有量化目标的性能优化

## 变体 C · 测试友好重构(为补单测铺路)

在【重构方案】后追加:
```
【可测性提升】
- 哪些函数拆出后可独立 mock
- 哪些依赖应注入而非硬编码
- 哪些副作用(IO/时间/随机)需要抽接口
```

适用:老代码准备补单测、TDD 改造前的清理
