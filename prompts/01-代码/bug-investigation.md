# Bug 定位与根因分析

> 场景:对一段报错/异常/行为不符预期的代码做系统性根因定位,产出可执行修复路径
> 适用模型:Claude (Sonnet/Haiku)、GPT-4o 均可 · 国内模型需附更多上下文
> 难度:⭐⭐⭐
> 作者/日期:31-智能 cron · 2026-08-26

## 提示词

```
你是一位资深<语言>工程师,擅长系统性排查 Bug。请基于以下信息,按"症状 → 假设 → 验证 → 根因 → 修复"五步定位。

【背景】
- 现象:<报错堆栈 / 异常行为描述>
- 触发条件:<输入 / 操作步骤 / 环境(OS/版本/配置)>
- 期望行为:<应发生什么>
- 实际行为:<实际发生了什么>
- 已尝试:<做过哪些排查,结果如何>
- 相关代码片段:<贴关键代码,标注行号或函数名>

【分析要求】
1. **症状归类**:先把现象归为"语法 / 运行时 / 逻辑 / 性能 / 并发 / 环境"六类之一
2. **假设树**:基于症状,枚举 ≥ 3 个可能根因,按可能性排序
3. **验证方法**:对每个假设,给出"如何快速验证"的方法(打 log / 加断点 / 跑最小用例)
4. **根因**:指出最可能的根因,给出证据链
5. **修复方案**:提供最小改动版 + 完整重构版两种方案,标出 trade-off

【输出格式】
```
【症状归类】<六类之一>
【假设树】
1. <假设 A>:可能性 70% — <理由>
   验证:<方法>
2. <假设 B>:可能性 20% — <理由>
   验证:<方法>
3. <假设 C>:可能性 10% — <理由>
   验证:<方法>
【根因】<一句话>
【证据链】<step1→step2→step3 推理过程>
【修复方案 A · 最小改动】
<代码 + 1 句说明>
【修复方案 B · 完整重构】
<代码 + 1 句说明>
【Trade-off】A 改动小风险低但留技术债;B 一劳永逸但需回归测试
```

【约束】
- 不要直接给"修这一行就行"的结论,必须走完五步
- 假设 ≥ 3 个,不能只有一个根因就下结论
- 验证方法必须可执行,不能写"看代码分析"
- 整体控制在 400 字以内
```

## 适用边界

- **适用**:
  - 单文件 / 单模块 / ≤ 500 行的 bug 定位
  - 报错堆栈清晰、能在本地复现的问题
  - 经典 OOM / NPE / 死锁 / 性能突降等可观测问题
- **不适用**:
  - 跨服务链路追踪(需 trace 系统配合,prompt 抓不到分布式上下文)
  - 偶发性 bug(出现概率 < 1%,需 runtime 监控数据)
  - 业务逻辑正确性(模型判断不了"是否符合业务规则")
- **已知坑**:
  - 模型对"环境差异"(OS / 依赖版本)的还原度低,需手动补全
  - 复杂并发场景模型易给出"加锁"这种过度简单的答案
  - 根因链 ≥ 3 跳时模型会丢失中间环节,需引导逐层追问

## 变体 A · 极简版(只输出根因 + 修复)

把【输出格式】替换为:
```
【根因】<一句话>
【修复】<最小改动代码>
```

适用:已知是常见 bug(空指针 / 数组越界 / 类型转换),快速求 fix

## 变体 B · 教学版(给初学者)

在【分析要求】前加:
```
【教学模式】每个步骤用 1 句话解释"为什么这样排查",帮助学习者建立排查思维。
```

适用:mentor 带新人 / 团队培训 / 沉淀排查 SOP

## 变体 C · 多文件版

把【相关代码片段】改为:
```
【相关代码】
- 文件 1:<路径:行号 范围> + 关键代码
- 文件 2:<路径:行号 范围> + 关键代码
- 调用链:<A → B → C,标注每跳的关键参数>
```

适用:跨文件 bug(典型:前端 → API → Service → DB 调用链)
