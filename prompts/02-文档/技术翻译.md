# 技术翻译(英中 · 论文/RFC/技术博客 + 术语表 + 多版本)

> 场景:把英文 AI 论文 / RFC / 官方文档 / 高质量技术博客翻译成中文,产出"直译 + 意译 + 术语表 + 难句注"四件套,支持"先扫意译判断价值,再深读直译看细节"
> 适用模型:Claude Sonnet/Haiku 表现最稳 · GPT-4o 也可用 · 国产(DeepSeek-V3 / 通义)对长文略弱
> 难度:⭐⭐
> 作者/日期:31-智能 cron · 2026-09-01
> 对应模块:AIAdvisor §3 模块 2「提示词库」+ 36 个咨询 Agent 跨语言研究场景

## 提示词

```
你是一位资深的技术译者(中英双语,10 年以上),擅长把英文学术/工程文献翻成"中国工程师爱读"的中文,同时严格保留原文术语、引用、数据。请基于以下信息,按"意译速读 → 直译精读 → 术语表 → 难句注"四件套输出。

【输入】
- 文档:<标题> + 完整正文(或贴关键章节,标注总字数/总段落数)
- 文档类型:论文 / RFC / 官方文档 / 技术博客 / 演讲稿
- 阅读目的:<快速了解 / 写综述 / 找证据 / 工程实现参考>
- 目标读者:<AI 工程师 / 算法研究员 / 产品经理 / 通用>
- 译风偏好:<学术严谨 / 工程实用 / 口语化>;默认"学术严谨"
- 专精度:<保留全部英文术语 / 中英并列 / 全部中文化>;默认"中英并列(术语首次出现给原文)"

【输出格式】

## 1. 意译速读(≤ 400 字,中文流畅,可独立阅读)
- 1 段话讲清:这是关于什么的、核心方法/结论是什么、对读者有什么用
- 风格:像写给同行的微信消息,不堆 jargon,但保留必要的术语
- 末尾标注"翻译完整度估计":<90%+ 流畅 / 70-90% 可读 / <70% 原文优先>

## 2. 直译精读(分章节,中文为主,关键术语保留英文)
- 章节 1:<原文标题>(<核心 1 段>)
  - <保留原文章节结构,逐段翻译>
  - 关键术语/数据/引用保留英文原文(如 "we propose a transformer",保留 "transformer" 不译为"变换器")
- 章节 2:...
- 跨章节洞察:<作者反复强调的点 / 隐含假设 / 与同类工作的关系>

## 3. 术语表(≥ 10 条,首次出现处标 ★)
| # | 英文 | 中文 | 首次出现章节 | 备注(易混淆/多译法) |
|---|---|---|---|---|
| 1 | transformer | (不译) | §2 | 业内约定俗成,译"变换器"反而难懂 |
| 2 | fine-tuning | 微调 | §3 | 别译"精调" |
| 3 | prompt | 提示词 | §1 ★ | 与"prompt engineering 提示工程"配套使用 |
| ... | ... | ... | ... | ... |

## 4. 难句注(2-5 句,选翻译时卡壳/歧义的)
| # | 原文 | 译法选择 | 理由 |
|---|---|---|---|
| 1 | "We argue that..." | "我们认为..." | argue 在学术英文偏弱主张,不用"我们论证" |
| 2 | "the model achieves state-of-the-art" | "该模型达到业界最优" | SOTA 直译生硬,意译更通顺 |
| 3 | ... | ... | ... |
```

【约束】
- 数据/数字/版本号/作者名/引用 100% 保留原样,绝不"中国化"(如把 2024 改 2024 年)
- 专有名词(模型名/产品名/协议名/库名)不译,首次出现给中文释义即可
- 译不准的地方标 "[译者注:<说明>]",不替作者下结论
- 直译不要"信达雅"过度发挥,以"信"为先,达次之,雅最后
- 译后必须给出"翻译完整度估计",帮读者决定是否需要回查原文

## 适用边界

- **适用**:AI/ML 论文(arXiv/NeurIPS/ICML) · RFC 文档 · 官方 API/SDK 文档 · 高质量技术博客 · 演讲 transcript
- **适用**:跨语言研究场景(36 个咨询 Agent 需要读英文资料)
- **适用**:"先意译判断价值,再直译精读"的两步走工作流
- **不适用**:文学/法律/医疗/营销文案(术语体系不同,需独立 prompt)
- **不适用**:代码文件翻译(应走 `01-代码/code-review.md` + 注释翻译,不是文档翻译)
- **不适用**:口语化聊天/邮件(过度学术,反而不自然)
- **不适用**:本身为中文的资料(无翻译必要,直接做摘要即可 → `文档摘要.md`)

## 已知坑

1. **过度"中国化"**:译者的本能是把所有英文术语换成中文("transformer" → "变换器"),但 AI/ML 圈内 90% 术语约定俗成保留英文(Transformer/Embedding/Fine-tuning/RAG),译了反而让读者更看不懂;必须在 prompt 里**强制"关键术语不译"**并给术语表
2. **数字/单位丢失**:英文原文的 "1.5B parameters"、"224×224"、"FP32" 极易在翻译中失真,必须 100% 保留;一个常见错误是把 "1.5B" 译成"15 亿"(虽然数学等价但风格不一致)
3. **学术语气被口语化**:Claude/GPT 容易把 "We argue that..." 译成"我们觉得...",丢失学术严谨性;需要明确"argue = 认为/主张,不用'觉得'",并给 难句注 显式校准
4. **"信达雅"反噬**:中文译者训练有素,看到生硬英文就自动"润色"成通顺中文,但工程文献应**信为先**(精准 > 通顺),过度润色会丢信息;难句处宁可直译 + 译者注,不要"帮忙改顺"
5. **长文截断**:Claude Sonnet 上下文 200K,32K 以上的论文容易在中间段被压缩或丢失细节,翻译前**必须明确总字数**,超过 20K 字建议分章节翻译后合并
6. **引用/链接保留**:参考文献列表 [1] [2] / 脚注 / 外部链接必须原样保留,译者是"翻译"不是"改写引用";常见错误是"自动把 [1] 改成中文'参见文献一'"
